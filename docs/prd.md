# Waypoint PRD

## 1. 개요

Waypoint는 창원시 버스 운영 데이터를 기반으로 운영자가 현재 운행 상태와 이상징후를 빠르게 파악하고, AI가 작성한 운영 브리핑을 확인할 수 있도록 돕는 업무용 웹 콘솔이다.

초기 제품은 챗봇이 아니라 운영 화면 안에 AI를 보조 기능으로 배치한다. 지연, 배차 간격, 위치 갱신 누락 같은 판단은 서버 로직이 계산하고, AI는 계산 결과를 운영자가 바로 이해할 수 있는 문장으로 변환한다.

## 2. 배경

창원시 버스 운영 업무에서는 실시간 위치, 도착 예정, 노선, 정류소 데이터를 함께 확인해야 한다. 단순 데이터 조회 화면만으로는 어떤 노선이 문제인지, 어느 구간부터 봐야 하는지, 오늘 어떤 상황을 우선 확인해야 하는지 빠르게 판단하기 어렵다.

Waypoint는 TAGO 공공 API 데이터를 수집하고, 운영 관점의 지표를 계산한 뒤, AI를 통해 사람이 읽기 쉬운 운영 브리핑을 제공한다.

## 3. 목표

- 창원시 버스 운영자가 현재 이상징후를 한 화면에서 파악한다.
- 노선, 정류소, 시간대별 위치 갱신 상태와 배차 간격 이상을 운영 지표로 계산한다.
- 서버가 계산한 이상징후를 AI가 운영자용 문장으로 요약한다.
- AI가 누적 수집 데이터를 함께 분석해 이상징후 임계값의 튜닝 후보와 근거를 보고한다.
- MVP에서는 권한 구분 없이 단일 운영자 화면으로 제공한다.
- MVP 수집 대상은 창원시 전체 노선으로 한다.

## 4. 비목표

- 초기 버전에서 범용 챗봇을 만들지 않는다.
- AI가 지연 여부나 원인을 단독 판정하지 않는다.
- 민원 검증, 자연어 검색 필터, 별도 데이터 상태 화면은 MVP 범위에 포함하지 않는다.
- 사용자/권한 관리 기능은 MVP 범위에 포함하지 않는다.
- 창원시 외 지역 확장은 MVP 범위에 포함하지 않는다.
- 배차 최적화나 운행 계획 자동 변경은 MVP 범위에 포함하지 않는다.
- AI가 이상징후 임계값을 자동으로 변경하지 않는다.

## 5. 사용자

- 버스 운영 담당자: 현재 운행 상태, 이상징후, AI 브리핑을 확인한다.

MVP에서는 사용자 역할을 나누지 않는다. 인증과 권한 구분은 추후 확장 시점에 다시 설계한다.

## 6. MVP 범위

### 6.1 운영현황

- 창원시 전체 노선별 현재 상태를 보여준다.
- 최근 위치 갱신 시각, 도착정보 수신 여부, 배차 간격 상태를 표시한다.
- 정상, 주의, 이상 상태를 구분한다.

### 6.2 이상징후

- 차량 간격이 과도하게 벌어진 노선을 탐지한다.
- GPS 위치가 오래 갱신되지 않은 차량 또는 노선을 탐지한다.
- 같은 노선 차량이 비정상적으로 붙거나 벌어진 구간을 표시한다.

### 6.3 AI 브리핑

- 서버가 계산한 이상징후 목록을 기반으로 운영자용 요약 문장을 생성한다.
- 현재 확인해야 할 노선, 영향 구간, 근거 지표를 함께 정리한다.
- 누적 데이터 분포를 기반으로 현재 임계값이 너무 민감하거나 둔감한 후보를 함께 보고한다.
- 원인은 확정하지 않고 데이터상 관찰된 패턴과 원인 후보로 표현한다.
- 임계값 조정은 제안으로만 제공하고, 실제 설정 변경은 운영자가 별도로 판단한다.

예시:

> 101번은 07:40부터 창원역 방면에서 차량 간격이 평균보다 크게 벌어졌습니다. 현재 영향 정류소는 창원역, 시청, 중앙동 구간이며, 후속 차량 위치 기준으로 앞차 지연 가능성이 있습니다.

## 7. 데이터

초기 데이터 소스는 TAGO 공공 API를 사용한다.

- 버스 노선정보
- 버스 도착정보
- 버스 위치정보
- 정류소 정보

운영 분석을 위해 API 응답은 이력 데이터로 저장한다. 최신 상태는 캐시를 사용할 수 있으나, MVP에서는 데이터베이스 저장과 단순 조회를 우선한다.

## 8. AI 적용 원칙

- AI는 판단 엔진이 아니라 설명, 요약, 초안 작성 보조 역할을 맡는다.
- AI 입력에는 서버가 계산한 구조화 데이터와 근거 지표를 포함한다.
- AI 출력에는 확정 표현을 피하고, 데이터상 관찰된 패턴과 원인 후보임을 드러낸다.
- AI 출력에는 임계값 튜닝 후보가 포함될 수 있으나, 이는 설정 변경 명령이 아니라 검토 대상이다.
- AI 출력은 운영자가 상황을 빠르게 읽기 위한 참고 정보로 제공한다.

## 9. 화면 구조

첫 화면은 통합 대시보드로 구성한다.

- 운영현황 요약
- 이상징후 목록
- AI 브리핑
- 임계값 튜닝 포인트

초기 화면은 대시보드형 업무 화면으로 구성한다. 마케팅용 랜딩 페이지나 채팅 중심 UI는 만들지 않는다.

## 10. 기술 방향

- Spring Boot: API 수집, 스케줄링, 통계 계산, 화면/API 제공
- Thymeleaf: 운영자 웹 콘솔
- Clean Architecture: domain/application/adapter/config 계층 분리
- MariaDB: 노선, 정류소, 도착정보, 위치정보 이력 저장
- H2: 로컬 개발용 데이터베이스
- Ollama: 운영 브리핑 생성
- Docker Compose: 로컬 실행 환경
- OpenAPI 문서: 내부 API 확인

## 11. 성공 기준

- 운영자는 오늘의 이상 노선과 영향 구간을 첫 화면에서 확인할 수 있다.
- 이상징후 목록은 서버 계산 결과와 근거 지표를 함께 보여준다.
- AI 브리핑은 서버가 계산한 이상징후 근거를 빠뜨리지 않고 자연어로 요약한다.
- AI 브리핑은 누적 데이터 기준의 임계값 튜닝 후보와 근거 분포를 함께 제시한다.
- 로컬 환경은 `local` 프로필로 실행할 수 있다.

## 12. 향후 확장

- 민원 검증 및 답변 초안
- 자연어 검색 필터
- 별도 데이터 상태 화면
- 도착 예정 시간 변동 기반 이상징후
- 운영 매뉴얼, 민원 처리 기준 문서 기반 RAG
- 주간 운영 보고서 자동 생성
- 정류소 또는 노선별 민원 다발 분석
- 지도 기반 차량 위치 및 영향 구간 시각화
- 사용자 인증과 권한 구분
- 창원시 외 지역 확장

## 13. 확정 설정

- 운영 DB는 MariaDB로 한다.
- 로컬 DB는 H2 `MODE=MariaDB`로 한다.
- TAGO 인증키는 `TAGO_SERVICE_KEY` 환경변수로 관리한다.
- 이상징후 임계값은 설정값으로 분리한다.
- Ollama endpoint는 `OLLAMA_BASE_URL` 환경변수로 관리하고 기본값은 `http://localhost:11434`로 한다.
- Ollama 모델은 `OLLAMA_MODEL` 환경변수로 관리하고 기본값은 `llama3.1`로 한다.
- 구현 구조는 클린 아키텍처로 한다.

## 14. 미정 사항

- 창원시 도시코드와 노선/정류소 기준 데이터 동기화 방식
- 이상징후 임계값 기본값
